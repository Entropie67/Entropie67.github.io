Langages et programmation Terminale

Comment on organise un programme (POO, paradigmes), comment on prouve qu'il fait ce qu'il doit (spécifications, assertions, tests), comment on trouve l'erreur quand il échoue, et pourquoi certains problèmes n'ont tout simplement pas de programme pour les résoudre.

1 Un programme, plusieurs façons de l'écrire

Depuis la Première, nous écrivons des programmes impératifs : une suite d'instructions qui modifient des variables (x = x + 1, boucles for…). Mais ce n'est pas la seule façon de penser un calcul. Deux autres styles reviennent sans cesse en Terminale :

Impératif

On dit à l'ordinateur comment faire, étape par étape. Variables, boucles, tableaux modifiés en place.

x = 0; for i in t: x = x + i

Fonctionnel

On compose des fonctions qui ne modifient rien. Pas d'effet de bord ; une fonction appelée deux fois rend le même résultat.

sum(map(carre, t))

Orienté objet

On regroupe données et actions dans des objets. Chaque objet connaît son état et ce qu'il sait faire.

compte.deposer(100)
Définition — paradigme de programmation

Un paradigme est une façon d'organiser le code et de penser le calcul. Python est multi-paradigme : on peut y mélanger les trois styles. L'important n'est pas d'en choisir un pour toujours, mais de savoir reconnaître lequel se prête à quel problème.

Dans ce chapitre, nous entrons en détail dans le paradigme orienté objet — le plus demandé au bac — puis nous donnons un aperçu du fonctionnel. Les parties 6 à 8 reviennent sur ce qu'on écrit autour du code (spécifications, tests, débogage), et la partie 9 montre, par un théorème, pourquoi tout n'est pas programmable.

2 La programmation orientée objet (POO)

Définition

Une classe est un modèle qui décrit un type d'objets : les attributs qu'ils portent (leurs données) et les méthodes qu'ils savent faire (leurs fonctions). Un objet est une instance concrète de la classe. De la classe Chien on peut créer autant d'objets que de chiens individuels : Rex, Médor, Fido…

L'analogie classique : la classe est le moule à gâteau, les objets sont les gâteaux qu'on en fait. Un même moule peut produire mille gâteaux ; chaque gâteau a sa propre vie.

Un premier exemple : la classe Point

class Point:
    def __init__(self, x, y):      # le constructeur : fabrique un nouveau Point
        self.x = x                      # attributs d'instance
        self.y = y

    def distance(self, autre):      # une méthode
        dx = self.x - autre.x
        dy = self.y - autre.y
        return (dx * dx + dy * dy) ** 0.5

# Création de deux objets Point
a = Point(3, 4)
b = Point(0, 0)

a.x                 # → 3     : on lit un attribut
a.distance(b)       # → 5.0   : on appelle une méthode sur l'objet a
Trois mots à retenir
  • Classe : le modèle (ce que savent tous les Points).
  • Instance (ou objet) : un exemplaire concret (a, b).
  • self : à l'intérieur d'une méthode, désigne l'objet sur lequel la méthode a été appelée. a.distance(b) appelle la méthode avec self = a et autre = b.

Le constructeur __init__

C'est la méthode spéciale que Python appelle automatiquement au moment de la création d'un objet. C'est elle qui donne leurs valeurs initiales aux attributs. Un objet qui n'a pas été correctement initialisé est une source classique de bugs.

Méthode ou fonction ?

Une fonction prend ses données en arguments et rend un résultat ; une méthode est une fonction attachée à un objet : elle agit sur ses attributs (via self) et éventuellement en lit ou modifie l'état.

distance_point(a, b)        # style fonctionnel : la fonction prend les objets
a.distance(b)                # style OO : on demande au point a sa distance à b

3 Encapsulation : cacher pour mieux protéger

Définition

L'encapsulation est le principe selon lequel un objet ne doit être modifié que par ses propres méthodes. L'extérieur ne touche pas directement aux attributs : il passe par l'interface que la classe lui offre.

Exemple : un compte bancaire. Rien n'empêche d'écrire compte.solde = -1000000… sauf qu'on ne veut précisément pas ça. On préfère exposer deux méthodes qui, elles, vérifient :

class Compte:
    def __init__(self, titulaire):
        self.titulaire = titulaire
        self._solde = 0          # convention : _nom = "ne touchez pas directement"

    def deposer(self, montant):
        if montant <= 0:
            raise ValueError("montant positif attendu")
        self._solde += montant

    def retirer(self, montant):
        if montant > self._solde:
            raise ValueError("solde insuffisant")
        self._solde -= montant

    def solde(self):
        return self._solde       # accès en lecture seule

c = Compte("Alice")
c.deposer(100)
c.retirer(30)
c.solde()                     # → 70
Attention — Python ne force rien

À la différence de Java, Python n'a pas de vraie protection : un _solde précédé d'un underscore peut toujours être lu ou écrit de l'extérieur. L'underscore est une convention sociale : il dit « ne touche pas, tu casseras quelque chose ». La protection vient de la discipline de qui utilise la classe, pas du langage.

Ce que l'encapsulation apporte

  • L'objet reste toujours dans un état valide (ici : solde ≥ 0).
  • On peut changer l'implémentation interne (par exemple ajouter un historique des opérations) sans toucher au code qui utilise la classe.
  • Le code appelant est plus court et plus lisible : c.deposer(100) plutôt que la logique étalée partout.

4 L'héritage : spécialiser une classe

Définition

Une classe fille (ou sous-classe) hérite d'une classe mère : elle reprend automatiquement tous ses attributs et toutes ses méthodes, et peut en ajouter ou en redéfinir (polymorphisme).

Un exemple : des formes géométriques

class Forme:
    def __init__(self, nom):
        self.nom = nom

    def aire(self):
        raise NotImplementedError("à redéfinir dans les sous-classes")

    def decrire(self):
        return f"{self.nom} d'aire {self.aire():.2f}"

class Rectangle(Forme):              # Rectangle hérite de Forme
    def __init__(self, L, l):
        super().__init__("rectangle")   # appelle le constructeur de la mère
        self.L = L
        self.l = l

    def aire(self):                     # on redéfinit (polymorphisme)
        return self.L * self.l

class Cercle(Forme):
    def __init__(self, r):
        super().__init__("cercle")
        self.r = r

    def aire(self):
        return 3.14159 * self.r ** 2

formes = [Rectangle(3, 4), Cercle(5)]
for f in formes:
    print(f.decrire())      # la bonne méthode aire() est appelée pour chaque objet

Trois concepts d'un seul coup
  • Héritage : Rectangle(Forme) dit que Rectangle est une forme. Il récupère nom et decrire.
  • super() appelle une méthode de la classe mère depuis la fille — typiquement le constructeur.
  • Polymorphisme : aire() existe dans Forme mais est redéfinie dans chaque fille. Appeler f.aire() exécute la version adaptée à l'objet f, sans que le code appelant sache de quel type exactement il s'agit.
À utiliser avec modération

L'héritage sert à exprimer un lien « est un » : un rectangle est une forme. Si le lien est plutôt « a un » (une voiture a un moteur), on préfère la composition : la classe Voiture a un attribut Moteur. Hériter juste pour partager quelques méthodes finit souvent par introduire des bugs : trop d'héritage étouffe la lisibilité.

5 Un aperçu du paradigme fonctionnel

Définition

Dans le paradigme fonctionnel, une fonction pure rend un résultat qui ne dépend que de ses arguments, et ne modifie rien en dehors d'elle (ni variable globale, ni objet reçu, ni fichier…). Appelée deux fois avec les mêmes arguments, elle rend deux fois le même résultat.

# Pure : ne modifie rien, dépend seulement de n
def carre(n):
    return n * n

# Non pure : modifie la liste reçue (effet de bord)
def ajouter_zero(t):
    t.append(0)

# Non pure : dépend d'une variable globale
compteur = 0
def compter():
    global compteur
    compteur += 1
    return compteur

Les fonctions sont des valeurs comme les autres

En Python, on peut passer une fonction en argument, la ranger dans une liste, la renvoyer. Trois outils de la bibliothèque standard illustrent le style fonctionnel :

list(map(carre, [1, 2, 3, 4]))         # → [1, 4, 9, 16]
list(filter(lambda x: x > 10, [5, 12, 8, 20]))  # → [12, 20]
sum(map(carre, [1, 2, 3, 4]))              # → 30

Un lambda est juste une fonction écrite en une ligne, sans nom. Les compréhensions de listes jouent le même rôle avec une syntaxe plus pythonique :

[carre(x) for x in [1, 2, 3, 4]]              # → [1, 4, 9, 16]
[x for x in [5, 12, 8, 20] if x > 10]  # → [12, 20]
Pourquoi s'y intéresser
  • Les fonctions pures sont plus faciles à tester (il suffit de les appeler avec des entrées et de vérifier la sortie).
  • Elles sont plus faciles à paralléliser : pas d'état partagé, donc pas de collision entre threads.
  • Elles rendent le raisonnement plus simple : on remplace mentalement un appel par son résultat.

La récursivité, étudiée au chapitre 1, est le cœur du style fonctionnel : définir une fonction par un cas de base et une combinaison d'appels, sans variable mutable.

6 Spécifier une fonction

Avant d'écrire une fonction, on dit ce qu'elle fait. Cela paraît trivial — mais c'est précisément ce que l'on écrit mal ou pas qui finit en bug.

Les quatre points d'une spécification
  1. Signature : nom, types des arguments, type du résultat.
  2. Préconditions : les hypothèses sur les arguments. Si elles ne sont pas vérifiées, la fonction n'a aucune obligation de bien se comporter.
  3. Postconditions : ce que vaut le résultat, et ce que la fonction garantit à sa fin.
  4. Effets de bord : ce que la fonction modifie en dehors de son résultat (une liste reçue, un fichier, un compteur global…). Idéal : aucun.
def dichotomie(t, x):
    """Cherche x dans la liste triée t.

    Préconditions : t est une liste triée dans l'ordre croissant ;
                    x est comparable aux éléments de t.
    Postcondition : renvoie un indice i tel que t[i] == x,
                    ou -1 si x n'est pas dans t.
    Effet de bord : aucun — t n'est pas modifiée.
    Coût : O(log n)."""
    ...

Préconditions à l'exécution : les assertions

L'instruction assert vérifie, pendant l'exécution, qu'une condition est vraie. Si elle est fausse, le programme s'arrête avec une AssertionError et un message. C'est le moyen le plus simple de détecter très tôt une précondition violée.

def factorielle(n):
    assert n >= 0, "factorielle n'est définie que pour n ≥ 0"
    r = 1
    for k in range(1, n + 1):
        r *= k
    return r

factorielle(-3)   # → AssertionError: factorielle n'est définie que pour n ≥ 0

Invariant de boucle

Un invariant est une propriété qui reste vraie à chaque tour de boucle. Il sert à prouver qu'une boucle fait bien ce qu'elle doit. Pour la somme :

def somme(t):
    s = 0
    for i in range(len(t)):
        # Invariant : s = t[0] + t[1] + ... + t[i-1]
        s = s + t[i]
    # Après la boucle : s = t[0] + ... + t[n-1]
    return s

L'invariant est vrai avant la boucle (somme vide = 0), reste vrai à chaque passage (on ajoute t[i]), et après la boucle il entraîne la postcondition.

7 Tester systématiquement

Une spécification sans tests n'engage que celui qui l'écrit. Un test est un petit programme qui exécute la fonction sur un cas précis et vérifie le résultat. On l'écrit une fois et il protège le code pour toujours.

Les tests unitaires avec assert

def maximum(t):
    m = t[0]
    for x in t[1:]:
        if x > m:
            m = x
    return m

# Les tests, en dessous :
assert maximum([3]) == 3                      # cas particulier : un seul élément
assert maximum([1, 2, 3]) == 3                # max à la fin
assert maximum([3, 2, 1]) == 3                # max au début
assert maximum([1, 3, 2]) == 3                # max au milieu
assert maximum([-5, -2, -8]) == -2           # valeurs négatives
assert maximum([4, 4, 4]) == 4                # doublons
print("Tous les tests passent.")
Méthode — penser aux cas limites
  • Les cas de base : liste à un élément, chaîne vide, entier 0, arbre vide…
  • Les valeurs extrêmes : négatives, très grandes, nulles.
  • Les doublons et les cas où plusieurs réponses sont valides.
  • Les cas où la fonction doit échouer ou lever une exception.

Un bug qui a échappé aux tests, ajoutez un nouveau test qui le reproduit avant de corriger : il sera votre garde-fou pour qu'il ne revienne jamais.

La bibliothèque doctest

Permet d'écrire des tests dans la docstring de la fonction, sous forme d'exemples :

def pgcd(a, b):
    """Renvoie le plus grand commun diviseur de a et b.

    >>> pgcd(12, 18)
    6
    >>> pgcd(100, 25)
    25
    >>> pgcd(7, 11)
    1
    """
    while b != 0:
        a, b = b, a % b
    return a

if __name__ == "__main__":
    import doctest
    doctest.testmod()           # exécute tous les >>> de la docstring

Double avantage : la documentation est la suite de tests, et elle ne peut pas devenir fausse sans que les tests s'en aperçoivent.

8 Déboguer : trouver et comprendre l'erreur

Démarche
  1. Reproduire le bug : trouver l'entrée minimale qui le déclenche.
  2. Observer l'état des variables à des endroits bien choisis (print, débogueur).
  3. Isoler l'étape qui donne un résultat faux : par recherche dichotomique dans le code.
  4. Comprendre pourquoi — pas seulement « quoi ».
  5. Corriger, puis ajouter un test qui reproduit le cas initial.

L'outil le plus utilisé : print

def moyenne(notes):
    s = 0
    for n in notes:
        s += n
        print(f"n = {n}, s = {s}")   # sondage pendant le développement
    return s / len(notes)

À retirer avant la version finale. Pour un code qui doit rester bavard, on utilise le module logging, qu'on peut activer ou couper selon le besoin.

Un vrai débogueur : pdb

Ajouter breakpoint() à l'endroit douteux arrête le programme et ouvre une console interactive : on peut inspecter les variables, exécuter la ligne suivante (n), entrer dans un appel de fonction (s), continuer (c). Dans un IDE (VS Code, Thonny, PyCharm), tout cela se fait avec des points d'arrêt cliquables.

Les erreurs à savoir lire
  • NameError : variable ou fonction qui n'existe pas (faute de frappe, oubli d'un import).
  • TypeError : opération sur des valeurs incompatibles ("3" + 4).
  • IndexError : indice hors des bornes d'une liste.
  • KeyError : clé absente d'un dictionnaire.
  • ZeroDivisionError : division par zéro.
  • RecursionError : récursion trop profonde (voir chapitre 1).
  • AssertionError : une précondition a été violée.

La trace (traceback) part toujours de l'erreur et remonte vers l'appel qui l'a provoquée : à lire de bas en haut.

9 Calculabilité : ce qu'une machine ne peut pas calculer

Depuis le début de l'année, on a écrit des programmes et étudié leur coût. Mais une question plus profonde se pose : existe-t-il des problèmes pour lesquels aucun programme ne peut exister ? La réponse est oui, et elle a été démontrée en 1936 par Alan Turing.

La machine de Turing

Avant même l'invention des ordinateurs, Turing a défini un modèle de calcul abstrait, extrêmement simple :

  • un ruban infini découpé en cases, chaque case portant un symbole ;
  • une tête de lecture-écriture qui pointe sur une case ;
  • un état interne (comme la ligne courante d'un programme) ;
  • un programme, c'est-à-dire une table de transitions : « dans l'état e, en lisant le symbole s, écrire s', se déplacer d'une case à gauche ou à droite, passer dans l'état e' ».

Thèse de Church–Turing

Tout ce qu'un ordinateur « raisonnable » (Python, un smartphone, un supercalculateur, votre calculatrice avec les boucles) peut calculer, une machine de Turing sait le faire aussi — simplement plus lentement. C'est une thèse (admise, non démontrable) : la notion intuitive de « calculable » coïncide avec celle de « calculable par une machine de Turing ».

Autrement dit : tous les langages sont équivalents en pouvoir expressif. Le choix du langage change le confort et la vitesse, jamais ce qui est calculable.

Le problème de l'arrêt

Imaginons un programme magique halte(P, e) qui, pour tout programme P et toute entrée e, renvoie True si P finit par s'arrêter sur l'entrée e, et False s'il boucle à l'infini. Un tel outil serait précieux : on vérifierait toute récursion, toute boucle.

Théorème de Turing (1936)

Un tel programme halte n'existe pas. Il n'y a aucun algorithme qui, en analysant le code d'un programme et une entrée, décide à coup sûr si ce programme finira ou bouclera.

Pourquoi — l'idée de la preuve

Supposons qu'un tel halte existe. Construisons alors ce programme malicieux :

def piege(P):
    if halte(P, P):              # si P appliqué à son propre code s'arrête…
        while True:                 # …alors on boucle,
            pass
    else:                          # et si P boucle…
        return                     # …alors on s'arrête.

Que se passe-t-il quand on appelle piege(piege) ? S'il s'arrête, alors halte(piege, piege) doit avoir renvoyé True — donc on est entré dans la boucle infinie, ce qui contredit « il s'arrête ». Et s'il ne s'arrête pas, alors halte a renvoyé False — donc on est passé par le return, ce qui contredit « il ne s'arrête pas ». Contradiction dans les deux cas : notre hypothèse initiale (halte existe) est fausse.

Conséquences très concrètes
  • Il n'y aura jamais d'antivirus parfait : décider si un programme est inoffensif revient à décider s'il s'arrête, et c'est indécidable.
  • Il n'y aura jamais de compilateur qui garantit qu'un programme ne contient aucune boucle infinie.
  • En pratique, on contourne avec des analyses partielles : on détecte certaines boucles, on prouve la terminaison de certaines récursions. Mais pas toutes.

D'autres problèmes sont indécidables : vérifier automatiquement qu'un programme est correct, décider si deux programmes calculent la même fonction, prouver mécaniquement n'importe quel théorème mathématique… C'est le théorème d'incomplétude de Gödel (1931), dont Turing a donné quelques années plus tard une version informatique.
